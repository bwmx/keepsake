# Keepsake: can Algorand keep a secret?

*A proof of concept of Benhamouda et al.'s evolving secret-holding committees, built on Algorand as it exists today. October 2026. Unreviewed research code; use synthetic secrets only.*

## Summary

Public blockchains are good at keeping records and bad at keeping secrets: everything on chain is visible to everyone, forever. Benhamouda, Gentry, Gorbunov, Halevi, Krawczyk, Lin, Rabin and Reyzin ("Can a Public Blockchain Keep a Secret?", [eprint 2020/464](https://eprint.iacr.org/2020/464)) showed how a chain's own stakeholders could hold a secret anyway. A committee drawn at random and in secret holds the secret in shares. Each epoch it hands the shares to a fresh committee and erases its own, and each member speaks only once, after it has nothing left to steal.

Keepsake implements that design on Algorand and uses it for **capsules**: a message locked for one recipient and a window of rounds, which expires for good afterwards. What we found:

- **It runs on Algorand without protocol changes.** One immutable smart contract and an off-chain member worker are enough. They use the block seed for sortition, `vrf_verify` to check it, app-call arguments as the broadcast channel, atomic groups for "speak once", and the BLS12-381 opcodes for fraud proofs.
- **It runs at production size.** On TestNet, committees of 216 seats with threshold 80, the size needed to tolerate a 5% corrupt share of the stake, ran four handovers in a row with every seat posting. A capsule opened 12 minutes after its recipient asked.
- **What it costs.** About 0.022 Algo of fees per seat per epoch, or 4.6 Algo per epoch for the whole committee, plus a refundable 0.15 Algo deposit per seat. With the trial's 27-minute epochs that is about 245 Algo a day; longer epochs cost proportionally less but make expiry coarser.
- **The paper's own parameters would not fit on a shared chain:** about 200 MB of handover data per epoch for a single key. Exact committee sizing, and packing every key into one dealing, bring four keys down to 12–15 MiB per epoch.
- **It is not secure yet in practice.** The cryptography is unreviewed and partly new. Penalties for cheating can be evaded. The trials ran every member on one machine, so they test mechanics and cost, not anonymity.

The code, tests and a local web demo are at [github.com/bwmx/keepsake](https://github.com/bwmx/keepsake).

## What a capsule is

A sender locks a message for one recipient and a window of rounds `[open, expires)`.
- **During the window,** the recipient asks for it from its wallet, receives decryption shares sealed to a fresh key, and decrypts locally. Nobody else learns anything.
- **After the window,** the key that could open it no longer exists: no committee holds it and none ever will again. Releases already delivered can still be decrypted by their recipient, and the sender always knew the message.

The same machinery could serve sealed-bid auctions, time-locked disclosure, or dead-man switches. Keepsake implements only private release to one recipient.

## How it works

The full walkthrough is in [design.md](design.md). In brief:

1. **Keys per time bucket.** The committee holds one key per *bucket*, a span of rounds. A capsule is encrypted to the public key of the bucket its expiry falls in, so handover cost grows with the number of live buckets, not the number of capsules. Bucket keys are generated by the committee itself, so nobody dealt them.
2. **Secret sortition.** Each epoch, members draw VRF tickets on the block seed, weighted by bonded stake. Each winning ticket creates a seat in the next committee, handed to a random member through a sealed one-time key. Nobody knows who holds a seat until it speaks.
3. **Speak once.** At the handover, each holder posts one message per seat: a re-sharing of its share of every bucket key to the next committee, contributions to new bucket keys, and decryption shares for requested capsules. Its secrets live in a short-lived process that exits before it posts. Everything in the message can be checked against public commitments, so the next committee takes the first t valid messages and ignores the rest.
4. **Expiry is forgetting.** A bucket that has ended is not re-shared, so after that handover no one holds it.

## Mapping the paper onto Algorand

| The paper needs | Algorand provides |
| --- | --- |
| Unbiased randomness for sortition | The block seed, read on chain with `block BlkSeed`. A proposer can only redraw it by withholding a block |
| Verifiable private lotteries | Members' own VRF keys, verified on chain with `vrf_verify` |
| Weight by stake | Bonds escrowed in the app, capped by online stake from `voter_params_get` |
| A broadcast channel | App-call arguments and notes, 20 KB per call at about 0.1 µAlgo per extra byte, rebuilt from blocks and checked against an on-chain digest per seat |
| Speak exactly once | One atomic group per seat: claim, message chunks and finalize land together or not at all |
| Holders that are anonymous until they speak | A seat's one-time key authorizes its holder's account at claim time; the holder's account posts only after its secrets are gone |
| Accountability for bad shares | BLS12-381 `ec_pairing_check` checks a reported share against its commitments on chain, for about 0.09 Algo at any committee size |

Nothing needs a node change, a precompile or a trusted operator. The randomness beacon and relayer of an earlier design are gone.

## What we learned

**Exact sizing beats the paper's bounds by about 45%.** The committee must be large enough that, with high probability, fewer than t of its seats are corrupt (secrecy) and at least t are honest (liveness). Computing exact Poisson tails instead of Chernoff bounds gives, at a 5% corrupt share and a 2^-64 failure chance per epoch, **216 seats with threshold 80** (with four packed buckets). The paper's bounds give 889. See [results.md](results.md#committee-size).

**Bandwidth was the first wall.** A plain handover re-shares every bucket separately. At the paper's parameters that is about 200 MB per epoch, and even at 210 seats it is 265 KB per seat per epoch with four live buckets. Alternating between handovers that pack every bucket into one dealing and handovers that unpack them again cut it to 55–72 KB per seat on TestNet, including the attested state and capsule releases. The price is a slightly larger committee (210 → 216 seats).

**Checking points costs more than the cryptography.** Every curve point a member receives must be checked to be in the right subgroup, and those checks cannot safely be batched. At production size this dominates verification. Members verify on every core. At 216 seats, one member's verification of a whole handover takes about 4–8 minutes of single-thread CPU, roughly 1–2 minutes on a 10-core laptop.

**Online stake alone is not a safe weight.** Stake can move between accounts while a nomination window is open and be counted once per account. Keepsake escrows a bond in the app; the weight is the bond, capped by online stake.

**Fraud proofs fit on chain but do not deter yet.** A holder signs a Merkle root over every (dealing, recipient) pair, and anyone can prove a bad share against it for about 0.09 Algo, slashing the holder's bond. But a careful cheater signs a root that leaves out its bad share, and is then just ignored like a silent member. Real deterrence needs a penalty for not delivering, such as the time-lock puzzles of [eprint 2026/919](https://eprint.iacr.org/2026/919).

**In the trials, the laptop was the bottleneck, not the chain.** At 216 seats, each of the five simulated members dealt for about 43 seats and verified every message, so one machine did the work of 216 members' dealing and five members' verification. Holders finished posting up to 185 rounds into the 220-round window, and members finished verifying 3–6 minutes after it. Rounds stayed at 2.70 s throughout. A real member holding one seat deals once (about 7 s) and verifies for a minute or two on a 10-core machine.

**Operations matter as much as cryptography.**
- **Public nodes rate-limit.** The first 60-seat run failed when the node rate-limited the members' reads.
- **Speak once, atomically.** Posting each seat as three separate transactions was too slow to fit the window; one atomic group per seat fixed it.
- **Windows must scale with seats per member.** With a 40-round nomination window, members holding about 43 tickets each missed about 5% of their nominations, and 60 rounds fixed it.
- **Reading state takes minutes at full size.** Reading the attested state means rebuilding about 12 MiB of messages from blocks. The first 216-seat run failed when the trial chose a capsule's opening round before that read, and the round had passed by the time it registered.

## Results

All TestNet runs used throwaway members on the public AlgoNode node, with rounds of about 2.7 s.

| Date | Seats per committee | t | Epoch | Handovers | Data per handover | Capsule: request to plaintext | Fees |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-10-10 | 5 | 2 | 60 rounds | 5, every seat posted | — | 250 s | 0.56 Algo over 5 epochs |
| 2026-10-11 | 60 | 20 | 150 rounds | 4, every seat posted | 2.6–2.9 MiB | 138 s | 5.54 Algo over 4 epochs |
| 2026-10-13 | 215–216 | 80 | 600 rounds (27 min) | 4, every seat posted, margins 132–136 | 11.5–14.8 MiB | 719 s | 21.0 Algo over 4 epochs |

Every run had five members, so in the last one each member held about 43 seats. Handovers alternated pack and unpack, and the capsule was released at the next handover after its request. An earlier 216-seat attempt ran two handovers, with every seat posting, before the trial's capsule step failed on the timing bug above. Details of every run are in [results.md](results.md#testnet-trials).

At production size, a seat's fees per epoch come to about 0.022 Algo:
- **Nomination, 0.011 Algo:** the VRF check's opcode budget and the deposit payment. This is about half the total.
- **Message chunks, 0.0085 Algo:** 3.25 chunks of up to 20 KB per message on average.
- **Claim and finalize, 0.002 Algo.**

Each seat also locks a 0.15 Algo deposit, returned about three epochs later.

## What this does not show

- **Security.** The pairing-based re-sharing and capsule encryption are our own construction and unreviewed. Plain ElGamal has no proof of the selective-opening security the paper requires, and the anonymity of HPKE rests on the paper's unproven Conjecture 1. See [security.md](security.md#open-questions-for-review).
- **Anonymity.** Every trial ran five members, each holding dozens of seats, on one machine. Anonymity needs thousands of independent members on their own nodes.
- **Deterrence.** Silence and carefully hidden cheating go unpunished.
- **Durability.** One handover with too few honest seats loses every live bucket, permanently.
- **Erasure.** Secrets live in short-lived processes, but JavaScript cannot prove memory is wiped.
- **Incentives.** Members pay fees and compute and earn nothing. The paper assumes a chain's stakeholders do this as part of running it.

## What would come next

1. **Independent members.** Run members on separate machines and nodes, ideally by different people. This removes the biggest caveat of the trials, and spreads the CPU, which on one machine was the limiting factor.
2. **Review.** Write the construction up as a short, self-contained spec for a cryptographer, or replace it with a published construction that has a proof.
3. **Deterrence and smaller committees.** Time-lock puzzles for non-delivery and fixed-size sortition, as in eprint 2026/919, which reports committees of about 100.
4. **Incentives or protocol integration.** Either reward members, or let consensus participants run the committee as part of the protocol.

## Reproducing

```sh
(cd crypto && npm ci --ignore-scripts && npm test && npm run params)
algokit localnet start
cd chain && npm exec --yes --package=pnpm@12.6.0 -- npm ci
npm test        # LocalNet tests
npm run demo    # Capsule Lab at http://127.0.0.1:8787
```

The TestNet trial needs a funded TestNet account in `.env`; see [chain/README.md](../chain/README.md#testnet-trial). The production-size run used:

```sh
TRIAL_MEMBERS=5 TRIAL_TICKETS=216 TRIAL_T=80 TRIAL_EPOCH=600 TRIAL_NOMINATION=60 \
TRIAL_HANDOVER=220 TRIAL_FUND=50 npm run trial
```
